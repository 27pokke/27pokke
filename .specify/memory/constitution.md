# 27pokke Constitution

## Core Principles

### I. コード品質は完成条件

すべての変更は、読みやすい命名、単一責任、明示的なエラー処理、重複の排除を
満たさなければならない（MUST）。利用可能なフォーマッター、リンター、型検査は
警告を放置せず通過しなければならない（MUST）。未使用コード、根拠のない複雑さ、
意図を隠す短縮表現を残した変更は完成とみなさない。品質は後工程ではなく、変更の
受け入れ条件そのものである。

### II. 変更にはテスト証拠を伴う（非交渉）

外部から観測できる振る舞いを追加または変更する場合、その振る舞いを検証する自動
テストを同じ変更に含めなければならない（MUST）。不具合修正では、修正前に失敗し、
修正後に成功する回帰テストを用意しなければならない（MUST）。境界、失敗経路、外部
連携はリスクに応じて単体テスト、統合テスト、またはワークフロー検証で覆う。実装を
通すためにテストを削除、無効化、または弱体化してはならない（MUST NOT）。

### III. 単純さと保守性を優先

要件を満たす最小で直接的な設計を選ばなければならない（MUST）。新しい依存関係、
抽象化、設定項目には、現在の具体的な必要性と保守コストを上回る利点を示さなければ
ならない（MUST）。将来の可能性だけを理由とした汎用化を避け、重複する知識は単一の
責任ある場所へ統合する。コメントはコードの動作ではなく、判断理由や制約を説明する。

### IV. 安全でレビュー可能な変更

変更は一つの目的に絞り、レビュー担当者が影響範囲と検証結果を追跡できる大きさに
保たなければならない（MUST）。既存の公開インターフェース、データ形式、設定、
自動化の契約は原則として後方互換にする。破壊的変更が不可避な場合は、影響範囲、
移行手順、ロールバック方法を実装前に明記しなければならない（MUST）。

### V. 文書化と運用可能性

利用方法、設定、公開動作が変わる場合、関連する文書と例を同じ変更で更新しなければ
ならない（MUST）。自動化は決定的に再実行でき、失敗時に原因を特定できる出力と非ゼロ
終了を提供しなければならない（MUST）。秘密情報や環境固有値をコードまたはリポジトリへ
埋め込んではならない（MUST NOT）。将来の保守担当者が安全に診断、変更、復旧できる
ことを運用可能性の基準とする。

## 品質基準

- すべての受け入れ条件は、対応する自動テストまたは再現可能な検証手順を持つこと。
- 標準のフォーマット、静的解析、型検査、テストをすべて通過すること。
- 外部契約、永続化形式、ワークフロー境界の変更には統合検証を含めること。
- セキュリティ、プライバシー、秘密情報への影響を変更ごとに確認すること。
- 品質ゲートの例外は、理由、リスク、期限、解消条件を記録した場合に限ること。

## 開発ワークフローと品質ゲート

1. 実装前に、期待する振る舞い、受け入れ条件、影響範囲を仕様または変更説明へ記録する。
2. テスト可能な単位で実装し、各単位でフォーマット、静的解析、関連テストを実行する。
3. レビューでは、要件との対応、失敗経路、互換性、複雑さ、文書更新を確認する。
4. マージ前に全品質ゲートを通し、実行した検証と結果をレビュー可能な形で残す。
5. マージ後に問題が判明した場合、まず再現テストを追加し、原因と再発防止を記録する。

## Governance

本憲章は、プロジェクト内の他の慣習や個別判断に優先する。改定には、変更理由、影響を
受ける原則、既存作業への移行方法を文書化し、レビューで承認を得なければならない
（MUST）。

バージョンはセマンティックバージョニングに従う。原則の削除または互換性のない再定義は
MAJOR、新しい原則や実質的なガイダンスの追加は MINOR、意味を変えない明確化は PATCH と
する。すべての機能仕様、実装計画、タスク、レビューは本憲章への適合を確認しなければ
ならない（MUST）。逸脱は、理由、リスク、承認者、解消期限を明記した一時的な例外として
のみ許可する。憲章は重要な運用変更時、かつ少なくとも各主要リリース前に見直す。
